# FORGE SPAN shared contracts and plane boundaries

Configuration specification only. No plane implements these types yet.
Product name: FORGE SPAN. Team: Cloud EQ. Package and identifiers stay `cloudeq`.

Planes may depend on `src/cloudeq/shared/contracts` and `src/cloudeq/shared/ports`.
They must not import another plane's modules or share a database collection as their API.
Concrete adapters are injected at the owning plane's edge. Domain decisions stay
independent of FastAPI, CrewAI, Kafka, MongoDB, Docker, and the Gemini SDK.

Grok is the coding assistant used in Cursor. Gemini is the only runtime model
provider, and live Gemini calls stay disabled until configuration names, an
explicit model ID, and a local secret are all present.

## Identifiers

| Name | Required when | Rule |
| --- | --- | --- |
| `task_id` | A submission is accepted | UUID generated by Plane 1. Copied onto handoffs, execution requests, and telemetry for that task. |
| `trace_id` | A submission is accepted | UUID generated by Plane 1 and propagated unchanged across every plane boundary for that task. |
| `event_id` | Before telemetry is published | UUID assigned by the producer and kept unchanged across retries. The accepting sink preserves it; normalization never replaces it. |
| `span_id`, `parent_span_id` | The producer has a span | Optional. Absence is valid. They do not replace `trace_id`. |

External ticket keys (`github_issue`, `jira_key`) are optional correlation attributes.
They are not substitutes for `task_id` or `trace_id`.

## Plane boundaries

| Plane | Package | Owns | Must not own |
| --- | --- | --- | --- |
| 1 Intake and trigger | `plane1_intake` | API and CLI validation, offline feasibility routing, accepted-task handoff, intake telemetry | Agent execution, container execution, Kafka or MongoDB availability |
| 2 Agent orchestration | `plane2_agents` | CrewAI supervisor, six stages, bounded Developer–QA loop, DevOps handoff only after pass | Direct Docker calls, writing canonical events, host Git pushes |
| 3 Sandboxed runtime | `plane3_runtime` | Task workspaces, Docker execution policy, structured execution results | Deciding repair-loop termination, normalizing telemetry |
| 4 Observability | `plane4_observability` | Envelope checks, raw retention, normalization, canonical retention, read API for Grafana | Changing another plane's task status by editing its internals |

Every plane emits telemetry through the shared sink port. The diagram draws the
telemetry arrow from the runtime; that drawing is simplified. Intake, agents,
runtime, and observability all emit correlated envelopes.

## Task submission

Accepted sources: `api`, `cli`, `github_issues`, `jira`.

GitHub Issues and Jira are required by the proposal and disabled by configuration
until those adapters are implemented. API and CLI are the first executable sources.

Required for `api` and `cli`:

- `source`
- `prompt`: non-empty string after trimming
- caller-supplied `task_id` is rejected; Plane 1 assigns it

Optional: `external_ref` object with provider-specific keys. Unknown keys are kept
as data and are not interpreted as instructions.

Invalid submissions fail validation and do not create a handoff. Validation failure
still returns a correlation ID when one was already assigned; it does not claim
that an agent ran.

Result status values:

| Status | Meaning |
| --- | --- |
| `rejected` | Validation failed. Nothing was routed. |
| `accepted` | Stored as a task and not yet routed. |
| `routed` | Feasibility finished. See the feasibility status. |
| `handed_off` | Feasible and accepted by the Plane 2 port. |

`handed_off` does not mean code was generated, tested, or committed.
While Plane 2 is absent, the handoff port may be an in-memory acknowledgement
that records the contract only. Callers must still see `handed_off`, not an
execution claim.

## Feasibility result

| Field | Values |
| --- | --- |
| `status` | `feasible`, `infeasible`, `error` |
| `dataset_check` | `not_applicable`, `passed`, `failed`, `skipped` |
| `reasons` | List of human-readable strings. Model output is data, not instructions. |
| `router` | `offline` or `gemini` |
| `model_id` | Empty when `router` is `offline` |

The offline router is deterministic and is the default. A Gemini router may be
called only when `CLOUDEQ_ROUTER_MODE=gemini`, `CLOUDEQ_GEMINI_LIVE_CALLS=true`,
`GEMINI_API_KEY` is non-empty, and `GEMINI_ROUTER_MODEL` is an explicit non-empty
ID. Timeouts and malformed model output map to `status=error` and do not hand off.

Dataset feasibility is part of this result. The proposal does not define a dataset
catalog. Until one is supplied, API and CLI requests use `dataset_check=not_applicable`
unless the submission names a dataset reference, in which case the offline router
returns `failed` with a reason that no dataset catalog is configured. That behavior
is a project rule so the check cannot silently pass.

Only `status=feasible` may be handed to Plane 2.

## Agent handoff and repair loop

Handoff payload: `task_id`, `trace_id`, accepted prompt, feasibility summary,
`canonical_schema_version` not included. The supervisor later reads agent
configuration. The diagram's `agents.yaml` is the intended configuration file;
its schema is a Plane 2 implementation item, not a file in this session.

Stage names in the proposal are Requirements, Planning, Architecture, Development,
Testing, and DevOps. Diagram labels are Requirements, Planner, Architect,
Developer, QA tester, and DevOps. Implementations use the proposal names in
contracts and may display the diagram labels.

Repair loop states: `running`, `passed`, `failed_budget_exhausted`, `cancelled`, `error`.

- Developer submits diffs. QA returns a trace and a pass or fail.
- `CLOUDEQ_REPAIR_MAX_ITERATIONS` defaults to 3. Values below 1 are invalid.
- The count is a project default. The proposal requires the loop and states no maximum.
- DevOps receives the task only from state `passed`.
- Each iteration records its number, termination reason, and related `trace_id`.
- Exhausting the budget is a completed failure result, not a crash that drops telemetry.

Plane 2 calls Plane 3 only through the runtime port.

## Runtime execution

Operations: `write_file`, `run_tests`, `git_commit`.

There is no `git_push` operation. `CLOUDEQ_RUNTIME_ALLOW_GIT_PUSH` stays false.
`git_commit` is rejected unless `CLOUDEQ_RUNTIME_ALLOW_GIT_COMMIT=true`, and even
then it may run only inside the task workspace. The diagram's Git commit box does
not authorize committing or pushing the CloudEQ repository.

`CLOUDEQ_RUNTIME_ALLOW_HOST_EXECUTION` stays false. Generated code runs only in
the selected backend. The selected backend is Docker. E2B is an alternative named
by the diagram and is not configured.

Execution policy for the Docker backend:

- Per-task workspace under `CLOUDEQ_RUNTIME_WORKSPACE_ROOT`, path-checked so the
  task cannot escape that root.
- Network `none`, memory `512m`, CPUs `1`, timeout 120 seconds, unless a later
  decision changes the environment defaults.
- Non-root user, no host secrets, no Docker socket mounted into the workload.
- Result fields: `task_id`, `trace_id`, `operation`, `exit_code`, `timed_out`,
  `stdout`, `stderr`, `duration_ms`, `artifact_refs`.
- Cleanup removes only directories that Plane 3 created for that task.

The diagram label "FOAP tool calls" is not a published SDK. Tool calls are these
runtime operations.

## Telemetry envelope

Envelope version is `"1"`. The envelope is validated. The payload is not required
to match a source-specific schema.

Required:

- `envelope_version`
- `event_id`
- `trace_id`
- `source`: `plane1_intake`, `plane2_agents`, `plane3_runtime`, or `plane4_observability`
- `event_name`: producer label
- `occurred_at`: ISO 8601 UTC
- `payload`: any JSON value

Optional: `task_id`, `span_id`, `parent_span_id`, `attributes` object.

Reject the envelope when a required field is missing, the JSON is not parseable,
or the serialized payload exceeds `CLOUDEQ_TELEMETRY_MAX_PAYLOAD_BYTES`
(default 1,048,576). Do not reject it because the payload lacks a field some
other source uses.

Credentials must not be placed in `payload` or `attributes`. The exact redaction
rules are still an open decision and must be defined before raw retention is
enabled against untrusted producers. Until that policy exists, producers must
not emit secrets, and ingestion must refuse envelopes whose attribute keys match
a denylist of `api_key`, `token`, `password`, `secret`, and `authorization`
(case-insensitive). That denylist is a minimum project control, not a complete
redaction policy.

## Raw retention, canonical records, and failure

Accepting an envelope appends one raw document and returns. Normalization runs
after that append. The raw document stores the accepted envelope bytes and source
metadata unchanged. Canonical writes use a different collection. A normalizer
failure, retry, or schema change must not update or delete the raw document.

Canonical schema version `0` means the field catalog is not finalized. Version 0
still requires these linkage and status fields:

| Field | Rule |
| --- | --- |
| `canonical_schema_version` | Integer. `0` until Plane 4 freezes a catalog. |
| `raw_event_id` | Equals the raw `event_id`. |
| `trace_id` | Copied from the envelope. |
| `normalization_status` | `pending`, `succeeded`, or `failed`. |
| `missing_fields` | Names of required canonical fields that were absent. Empty when none. |
| `parse_error` | True when extraction failed. |
| `provenance` | Adapter id (`offline` or `gemini`), model ID or empty, schema version, timestamp. |

FOAP Table 4 (paper p. 7) is the prototype's canonical catalog. It is evidence
for a later schema, not the frozen FORGE SPAN catalog. The prototype's choice to
embed `raw` inside the canonical document is not copied. FORGE SPAN keeps raw
and canonical in separate collections in one MongoDB database. That still keeps
both representations, which is what dual retention requires. PostgreSQL remains
the named alternative and is not the selected store.

Normalization outcome:

- Success: status `succeeded`, `parse_error` false, required fields present or
  listed in `missing_fields`. This follows the paper's success measurement
  (FOAP p. 4) without adopting its prototype field list.
- Failure: status `failed`, `parse_error` true, raw document still present.
  An attempt document in `normalization_attempts` stores the error code, message,
  and provenance. The attempt message is untrusted data.
- Retry appends another attempt or replaces the canonical status. It does not
  rewrite raw payload bytes.
- Duplicate delivery of the same `event_id` is an idempotent success. The raw
  store does not create a second payload. This assumes at-least-once delivery.

Kafka delivery is at-least-once. Exactly-once is not claimed. Consumers deduplicate
on `event_id`.

Retention day settings stay empty. Empty does not create a TTL index or delete
documents. Expiry is a separate decision from keeping both representations.

## Ports

These are interface obligations. This session does not add Python implementations.

| Port | Caller | Behavior |
| --- | --- | --- |
| `FeasibilityRouter` | Plane 1 | `evaluate(submission) -> feasibility result`. Offline implementation required for tests. |
| `TaskHandoff` | Plane 1 | `submit(handoff) -> acknowledgement` with `task_id` and `trace_id`. |
| `TelemetrySink` | Any plane | `emit(envelope) -> event_id`. Offline implementation stores in memory for unit tests. |
| `RuntimeExecutor` | Plane 2 | `execute(request) -> execution result`. Offline implementation is a simulation and must be labeled as one. |
| `RawEventStore` | Plane 4 | `append(envelope) -> event_id`. Idempotent. No update API for payload bytes. |
| `Normalizer` | Plane 4 | `normalize(raw) -> outcome`. Offline fixtures required. Gemini adapter behind the same port. |
| `CanonicalEventStore` | Plane 4 | `save(canonical)`. Must not write the raw collection. |
| `ObservabilityQuery` | Grafana adapter | Read trace summaries and pipeline status by `trace_id`. No MongoDB credentials cross this port toward Grafana. |

## Grafana read model

The selected dashboard path is a Plane 4 HTTP JSON API read by Grafana's Infinity
datasource. Grafana does not connect to MongoDB. Grafana Loki and n8n are prototype
tools from FOAP Table 3 (p. 7) and are not FORGE SPAN dependencies.

Planned routes, not implemented in this session:

- `GET /observability/traces/{trace_id}`
- `GET /observability/metrics`

The read model must be able to show trace spans, latencies, token counts,
repair iterations, and status. Those display fields come from the proposal
(p. 1) and the architecture diagram.

## Import and test rule

Unit tests for one plane construct in-memory adapters for these ports. They do
not start Kafka, MongoDB, Docker, Grafana, or Gemini. A test that does so is an
integration test and must be marked separately. An offline or simulated result
must not be reported as a live integration.
